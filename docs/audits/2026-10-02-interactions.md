# Interaction audit — 2 October 2026

## Scope and limits

Reviewed the implementation and the in-scope interactive families: `KnowledgeInteractions`, `AdaptiveLearning`, `ReferenceGuideExperience`, `ServiceKnowledgeLab`, `LearningSystem`, `ConnectedTastingRoom`, `TastingParticipantTools`, and `TastingHostConsole`. The review focused on whether a user can tell what a control changes, whether the outcome is announced, whether the action works by keyboard and on a narrow screen, and where personal state is stored or sent.

This is a source-level audit plus the shared application/browser observations recorded in `2026-10-02-browser.md`; it is not a production data or authorization test. I did not run the full build or a two-account browser session. Account separation described below is an implementation property, not proof against every auth transition or server response. Root is arranging independent browser evaluation and the combined build.

## Findings and changes

1. **High — personal browser interactions shared one unowned local namespace.** Guide notes/progress, participant answers, and host-console state could not distinguish guest data from signed-in accounts. Added `scopedInteractionKey` and used account IDs or a separate guest suffix. Legacy interaction keys are neither migrated nor displayed; their bytes remain untouched. The guide component remounts on article/account change.

2. **High — registration could claim old learning progress.** `repository.learning` is a personal record stored under the unscoped `vine-atlas-learning-v2` cache key. Registration previously treated every local personal key as owned by the new account when the server had no value. Registration now excludes learning from that migration and archives the raw legacy string under `vine-atlas-learning-v2:legacy-unassigned` (or a numbered sibling if needed), removing it from the active key before account state is loaded. The archive is never read by the application. No database or auth schema changed. Normal authenticated hydration remains server-authoritative; the two-account path still needs runtime verification.

3. **High — participant response sharing was broader than persistence scoping.** The old channel name depended only on tasting ID, so a host tab from another account in the same browser could receive a participant message. Participant and host now derive the channel name from the same guest/account-scoped key. The participant notice explains that saving sends its text and confidence to matching host consoles in the same browser and account/guest session; it is not account-synced as a response record. Local persistence must succeed before a signal is sent.

4. **High — comparison and simulator looked like the same interaction.** The browser audit observed repeated `System activity: temperature and available nutrients` headings and identical three-option feedback in the wine-as-system lesson. The renderer now consumes authored per-module A/B prompts, choices, and outcomes for `comparison-lab`; `sensory-lab` has its own three-choice perception task and localized observations; only `simulator` consumes the three-state profile control. The curriculum contract is populated for all 11 modules’ comparisons and four sensory scenarios. These tasks remain hypotheses/observations, not deterministic flavour claims.

5. **Medium — state/effect feedback was inconsistent.** Storage and save failures are now visible in participant, host, guide, adaptive-planner, and connected-room flows. The connected room distinguishes “could not save note” from “could not add wine,” rather than reporting the wrong failed action. Host reset copy distinguishes counts from observations. Learning/adaptive live text includes recommendation count and time, so changing preferences has an announced effect.

6. **Medium — route reuse could retain stale selections.** The connected tasting room remounts on invitation ID; study practice remounts on guide/account; service object labs remount on article ID; participant and host tools remount on their account-scoped storage keys. This prevents stale option indexes, prior users’ note drafts, or an old chapter’s state from appearing in the new context.

7. **Medium — mobile and keyboard affordances varied across local components.** Added one focused interaction stylesheet for explicit focus-visible outlines, a two-column A/B layout that stacks on narrow screens, minimum 44px participant/host/tasting-room targets, and contained horizontal scrolling for phase/flight rails. Native controls remain in use; no custom keyboard event layer was introduced.

## Persistence and privacy map

- **Ephemeral only:** KnowledgeInteractions controls; service lab selections; lesson A/B, sensory, simulator, timeline, and quiz answers. They do not persist as personal answers.
- **Local, guest/account-separated:** Reference guide notes and completion; participant answer drafts/reflections; host timer/counts/observations. Existing unknown-owner legacy values are not read. Participant signals are transient same-browser messages and contain response text/confidence by design.
- **Repository-backed personal state:** Learning bookmarks/progress/preferences, journeys, tasting notes, and cellar entries. These use `repository`; auth hydration clears/loads personal cache on ordinary account transitions. Registration no longer assigns unknown-owner legacy learning to a new account. This source review does not prove production API authorization or an account-switch sequence.
- **Public or catalog-derived:** Region/grape/wine selector metadata and object-lab examples are not personal answers.

## Source-accuracy follow-up

The grape catalog's acidity, tannin, and body values are generated by fixed heuristic sets in `src/data/catalog.ts`; they are not sourced tasting measurements. `GrapeDeepDive` no longer renders those values as a score or turns them into grape-specific cool-versus-warm climate claims. It shows normalized vine/fruit observations when available and otherwise gives a practical morphology comparison exercise. Its structure note asks learners to taste two wines at the same serving temperature and record acidity, tannin texture, body, and finish. The catalog values remain unchanged because other views may consume them.

`RegionFieldGuide` only renders soil-family cards for IDs in the explicit `regionTerroir` profile set; the country-level fallback soil string is not enough to expose a regional field guide. Its note distinguishes general material mechanisms from parcel measurements and wine-flavour predictions. `RegionTerroirStudio` in `KnowledgeInteractions` contains no soil claim: its named-region controls are a hypothetical model and now say their effects are neither measurements nor predictions for that region. Broader catalog-derived region/producer prose and the underlying fallback metadata were not rewritten in this targeted pass.

The follow-up comparison review covered all 11 authored A/B modules. Four outcomes needed a more concrete observation method: fermentation conditions now name density and temperature trends plus residual-sugar/YAN checks; vine water stress points to matched-time stomatal-conductance readings where available; harvest timing asks learners to compare consistent samples and record sugar, acidity, tissue taste and weather; fermentation progress distinguishes a density log from bubbles and calls for analytical residual-sugar confirmation. The guidance avoids prescribing a fixed cellar intervention.
